Official sources checked 2026-10-04:

- [YouTube Data API v3 search.list](https://developers.google.com/youtube/v3/docs/search/list): fixedGET search endpoint, snippet/video results, embed/syndication filtering, provider relevance order and project quota. The current page describes a Search Queries quota bucket; do not hardcode older quota costs or guarantee available quota.
- [YouTube embedding / privacy-enhanced mode](https://support.google.com/youtube/answer/171780?hl=en): website embeds may use youtube-nocookie. This changes provider personalization behavior; it does not promise no external contact/cookies. Restricted videos can still require external opening.
- [Official IFrame Player API](https://developers.google.com/youtube/iframe_api_reference): documented ready/error events and destroy lifecycle. No autoplay calls. No custom playback engine or npm player package; lazily load the official API only after Play.
- [Required minimum functionality](https://developers.google.com/youtube/terms/required-minimum-functionality): keep source Referer using strict-origin-when-cross-origin, minimum200×200 player, and no app overlay covering provider controls. Error153 can indicate missing client identity. Consequently narrow mobile player height is at least200px even when exact16:9 would be shorter; thumbnails remain16:9. External watch links retain noopener/noreferrer; they are separate from embedded player identity.
- [智谱 AI Search Engine / Web-Search-Pro](https://docs.bigmodel.cn/cn/best-practice/case/ai-search-engine): domestic search uses the official OpenAI-compatible chat completions route with `web-search-pro`; only validated Bilibili canonical URLs are retained.
- [Bilibili external player](https://player.bilibili.com/): the app locally builds `player.html?bvid=...` with documented `autoplay`, `poster` and `danmaku` parameters; it does not scrape or call undocumented Bilibili APIs.
- [Google API key restrictions](https://docs.cloud.google.com/api-keys/docs/add-restrictions-api-keys): restrict to YouTube Data API v3 and the actual browser origin (production https://king-640-060.github.io/*; allow development origins only if needed). Browser referrer restrictions are not secret concealment. The provider sends the Key using the official [X-Goog-Api-Key system parameter](https://docs.cloud.google.com/apis/docs/system-parameters), outside request/display URLs. Browser CORS/network/quota failures use fixed safe guidance, never proxy forwarding or automatic retries.

## Local boundaries

`VideoSearchConfigV2` is stored at `fitlog-video-search-config-v2`. The old YouTube key/config (`fitlog-video-search-key-v1`, `fitlog-video-search-config-v1`) is read during migration and never deleted. Bilibili uses a separate device-local key (`fitlog-video-search-bilibili-key-v2`) unless the active profile is explicitly marked as the compatible Zhipu preset and official base URL; model name alone never grants reuse. V2 privacy acknowledgement is independent because the scope now includes domestic search. All provider credentials and policy settings stay outside the business DB, Backup, Restore and Sync; known-secret guards cover both keys.

The single app-owned `search_training_videos({query,limit?})` tool routes through `TrainingVideoSearchRouter`. Supported providers are Bilibili via Zhipu Web-Search-Pro and the preserved YouTube Data API v3 adapter. Settings expose B站/YouTube toggles and `auto` (B站 first, immediate YouTube fallback only on empty/failure), `all` (parallel best-effort merge), or one-provider policies. A provider failure is a safe notice and does not erase successful results. No geolocation, language, timezone, VPN detection, scraping, undocumented Bilibili endpoint, Douyin, arbitrary URL, HTML or provider iframe string is accepted.

## Settings interaction contract

The Training Video Search settings sheet is a formal settings surface: a short explanation is followed by real accessible source checkboxes styled as switches. B站 is labeled “国内网络优先”; YouTube is labeled “需要可访问 YouTube 的网络”. Provider credentials and long notes are progressively disclosed only when that source is enabled. When both sources are enabled, the only visible strategy choices are automatic selection or searching all sources; when one source is enabled, persistence normalizes to that provider policy, and when both are off the sheet saves an explicit disabled state without a network test.

For a compatible active Zhipu profile, B站 shows the actual chat/tool identity as `provider · activeProfile.model` under “当前使用 / 复用当前 AI 配置”. Editable profile names and vision model IDs are never used as the chat identity. A quiet action reveals a separate domestic key without deleting it when the user switches back to profile reuse. Changing credential source invalidates that source’s prior connection result and requires a fresh test; the other provider’s status remains intact. An incompatible profile shows the reuse warning and the standalone key field directly. YouTube shows its key field only while enabled. Provider rows use `已连接 / 已配置 / 未配置 / 测试失败`; tests run independently so a successful source remains successful when another source fails. The privacy acknowledgement stays compact with a 44px target and becomes a quiet acknowledgement after confirmation.

Queries remain bounded exercise/technique keywords (120 characters, limit 1–5), with known-secret/private-context rejection. Bilibili accepts only `https://www.bilibili.com/video/BV...` canonical paths and derives watch/player URLs locally. YouTube keeps strict 11-character IDs and derives watch/embed/thumbnail URLs locally. Responses are bounded and projected to safe text; URLs never enter model metadata.

Cards are plain DOM/text, max5, source badges, bounded titles and44px actions. Play creates one provider-specific official iframe; Bilibili uses the documented external player, YouTube uses the official privacy-enhanced IFrame API. Another Play, close, Clear, `pagehide` or hidden-page cleanup destroys the prior frame. Both providers have a quiet load timeout and external fallback.

## Training journal

Training Journal is optional progressive disclosure on Strength and Cardio forms/details. It reuses `Workout.note` and `CardioSession.note`; no new store, migration, Backup version or Sync version exists. Existing text, line breaks and Unicode are preserved; outer whitespace is trimmed, empty values become `undefined`, and values over2000 characters are rejected. A blank record shows a quiet “添加训练日志” action; an existing record shows a compact readable block with edit. Completion never prompts. History and Calendar Day Detail show only a small “有训练日志” marker; Today has no new entry. Workout templates exclude journals and copied workouts start with no journal. AI READ summaries label notes as `user-authored journal` and `subjective`; AI may quote them but cannot diagnose or write them.

## Verification categories

Unit tests cover request flags/headers, missing configuration/consent, strict projection/IDs/URLs, malformed/oversized/error/secret/timeout/abort response, known-secret integration, tool metadata/artifact separation and duplicate calls. Browser suite mocks search and official player events while testing actual app controls/lifecycle across mobile fonts/widths. These tests do not prove a real Key, browser/provider compatibility, real playable videos or physical Safari/PWA. Real provider and physical playback remain Not performed/Pending until separately verified.
