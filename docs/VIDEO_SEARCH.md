## Local boundaries

`VideoSearchConfigV2` is stored at `fitlog-video-search-config-v2`. The old YouTube key/config (`fitlog-video-search-key-v1`, `fitlog-video-search-config-v1`) is read during migration and never deleted. Bilibili uses a separate device-local key (`fitlog-video-search-bilibili-key-v2`) unless the active profile is explicitly marked as the compatible Zhipu preset and official base URL; model name alone never grants reuse. V2 privacy acknowledgement is independent because the scope now includes domestic search. All provider credentials and policy settings stay outside the business DB, Backup, Restore and Sync; known-secret guards cover both keys.

The single app-owned `search_training_videos({query,limit?})` tool routes through `TrainingVideoSearchRouter`. Supported providers are Bilibili via Zhipu Web-Search-Pro and the preserved YouTube Data API v3 adapter. Settings expose B站/YouTube toggles and `auto` (B站 first, immediate YouTube fallback only on empty/failure), `all` (parallel best-effort merge), or one-provider policies. A provider failure is a safe notice and does not erase successful results. No geolocation, language, timezone, VPN detection, scraping, undocumented Bilibili endpoint, Douyin, arbitrary URL, HTML or provider iframe string is accepted.

## Settings interaction contract

The Training Video Search settings sheet is a formal settings surface: a short explanation is followed by real accessible source checkboxes styled as switches. B站 is labeled “国内网络优先”; YouTube is labeled “需要可访问 YouTube 的网络”. Home always retains two compact provider configuration rows. Toggles only change enabled state, status and policy copy, keeping measured height and shared body scroll stable; they never insert credential forms. Explicitly clicking a configuration row opens that provider editor in the same Sheet, preserving the home DOM/drafts/scroll. Disabled rows remain configurable without enabling the source. Back/Escape returns home, and editor Save/Enter only saves configuration, never tests. When both sources are enabled, the only visible strategy choices are automatic selection or searching all sources; when one source is enabled, the same policy slot shows static source copy and persistence normalizes to that provider policy, and when both are off the sheet saves an explicit disabled state without a network test.

For a compatible active Zhipu profile, B站 shows the actual chat/tool identity as `provider · activeProfile.model` under “当前使用 / 复用当前 AI 配置”. Editable profile names and vision model IDs are never used as the chat identity. A quiet action reveals a separate domestic key without deleting it when the user switches back to profile reuse. Changing credential source invalidates that source’s prior connection result and requires a fresh test; the other provider’s status remains intact. An incompatible profile shows the reuse warning and the standalone key field directly. YouTube shows its key field only inside its explicit credential editor. Provider rows use `已连接 / 已配置 / 未配置 / 测试失败`; tests run independently so a successful source remains successful when another source fails. The privacy acknowledgement stays compact with a 44px target and becomes a quiet acknowledgement after confirmation.

Queries remain bounded exercise/technique keywords (120 characters, limit 1–5), with known-secret/private-context rejection. Bilibili accepts only HTTPS root/www/mobile official video BV paths and canonicalizes to `https://www.bilibili.com/video/BV...` and derives watch/player URLs locally. YouTube keeps strict 11-character IDs and derives watch/embed/thumbnail URLs locally. Responses are bounded and projected to safe text; URLs never enter model metadata.

Cards are plain DOM/text, max5, source badges, bounded titles and44px actions. Play creates one provider-specific official iframe; Bilibili uses the documented external player, YouTube uses the official privacy-enhanced IFrame API. Another Play, close, Clear, `pagehide` or hidden-page cleanup destroys the prior frame. Both providers have a quiet load timeout and external fallback.

## Training journal

Training Journal is optional progressive disclosure on Strength and Cardio forms/details. It reuses `Workout.note` and `CardioSession.note`; no new store, migration, Backup version or Sync version exists. Existing text, line breaks and Unicode are preserved; outer whitespace is trimmed, empty values become `undefined`, and values over2000 characters are rejected. A blank record shows a quiet “添加训练日志” action; an existing record shows a compact readable block with edit. Completion never prompts. History and Calendar Day Detail show only a small “有训练日志” marker; Today has no new entry. Workout templates exclude journals and copied workouts start with no journal. AI READ summaries label notes as `user-authored journal` and `subjective`; AI may quote them but cannot diagnose or write them.

## Reliability and local cost boundary (2026-10-06)

The current official Web-Search-Pro example places results in choices[0].message.tool_calls[1].search_result with link/title/content/media/icon/refer, while message.content may carry text. The previously narrow structured-field projection could discard links in plain/Markdown content; this is an identified code limitation, not a confirmed account-specific real-service root cause. The synthetic frozen tests/fixtures/webSearchPro.json follows that official shape and produces two distinct BV videos; it is not a captured real response.

Projection extracts structured URL/link/href fields, bounded nested tool/search results, plain text, Markdown links and escaped slashes. Never accept provider iframe or thumbnail URLs. All provider text is untrusted and rendered as text.
