# FitLog Lite — ChatGPT × Codex 协作与交付规范

本文件是 FitLog Lite 长期协作流程的唯一主要来源。流程通过仓库文档恢复，不依赖某一次聊天的记忆。新任务先按根目录 [AGENTS.md](../AGENTS.md) 的顺序加载上下文，再实际读取本文件及任务相关合同。

协作版本：**V2 · ChatGPT-first（ChatGPT 优先）**。需求分析、方案比较、可交互原型制作与迭代、设计确认和开发指令编写尽可能在 ChatGPT 中完成；Codex 主要负责将已确认设计实现为生产代码、测试、兼容性验证、提交和授权发布。减少重复产品探索与返工，不得为了节省 Codex Token 降低工程安全性或跳过必要测试。

本规范约定需求如何进入开发、如何交付与验收，不替代现有业务、数据保护、测试、发布和设计合同。业务及数据安全合同始终具有优先约束力；协作流程不能成为弱化工程门槛或历史语义的理由。当前代码用于核实实现事实，不能据此擅自改变已确认需求或合同。

## 阶段 1：用户提出需求

- 用户可以使用文字、截图、视频或其他资料描述问题和期望。
- ChatGPT 首先理解需求，不直接生成正式开发指令。
- 涉及现有功能时，先检查当前实现，并区分：已实现、部分实现、未实现、回归问题。不能仅凭旧聊天重新安排已完成工作。
- 核实资料对应的版本与环境；无法读取相关代码或证据时明确说明限制，把待核实问题留给后续检查，不能宣称已经检查。

## 阶段 2：需求分析

ChatGPT 需要明确：

1. 当前问题及可确认的证据，包括相关页面、操作、版本和复现条件。
2. 用户期望的实际结果。
3. 可能的方案及各自优缺点。
4. 影响范围、数据风险和交互风险。
5. 可逐项验证的功能验收条件。

分析必须区分「已确认事实」「合理推测」「需要代码核实的问题」。推测应标注依据和验证方法，不得将猜测当作事实；用户截图、代码事实和自动化结果也不能互相代替。

## 阶段 3：用户确认

- 用户明确确认最终方案后，ChatGPT 才能生成正式开发指令。
- 未经确认不得擅自扩大需求，也不能借局部修复开展无关重构。
- 如果实施期间出现改变核心业务逻辑、数据语义或视觉方向的决策，应停止相关部分并请求用户确认；不受该决策影响且已授权的工作可以继续。
- 用户已经明确授权的事项不要求重复确认。用户直接提供完整、明确的正式开发任务时，按其中已确认的范围执行，无须重新走一遍方案讨论。

## 阶段 4：视觉原型（按需启用）

涉及明显视觉或交互变化时，**优先由 ChatGPT 直接制作并迭代原型**：

- ChatGPT 可以制作独立 HTML/CSS/JavaScript 可交互原型，提供可下载文件；用户直接在 ChatGPT 中查看、提出修改并确认最终版本。
- 在条件允许时，尽量使用项目现有颜色、字体、间距、视觉组件和交互规范，并优先复用已批准设计。
- 不要求每个微小视觉变化都制作完整 HTML，按下表选择适当的对照或原型；不应仅为了制作普通交互原型而调用 Codex。
- ChatGPT 环境无法完成的复杂原型，应先说明具体限制，并获得用户授权后再交给 Codex。
- 无视觉变化的业务逻辑任务不强制制作原型。

|变化范围|原型或对照方式|
|---|---|
|简单文字、颜色、局部间距|修改前后对照|
|卡片布局、页面层级|高保真手机原型|
|表单、弹窗、状态切换|可交互 HTML 原型|
|多页面复杂交互|完整的相关状态覆盖及跨页面操作原型|

原型要求：

- 优先复用项目已有设计 Token、组件规则和已批准原型，不得脱离当前项目自行创造一套新视觉体系。
- 覆盖本次需求相关的空状态、已有数据状态、错误状态及必要交互，不能只展示理想静态页面。
- 用户确认原型后才进入正式开发。修复已批准设计时，先读取并运行既有基准，无须让用户重复确认同一设计或重复上传可找回的资料。
- 已确认原型应提供明确文件位置、版本或 SHA256，并在开发指令中引用。批准版本应长期可访问，不能悄悄修改基准造成漂移。
- 本项目已有 [V4.2 设计参考说明](../design/reference/v4.2/README.md) 和原始 [V4.2 HTML 原型](../design/reference/v4.2/FitLog_V4_2_Prototype.html)。涉及该设计时遵循对应合同的读取、运行、校验及对照要求。
- 原型只定义交互与视觉预期。真实业务事实仍以生产服务和数据契约为准，不能复制演示数据、模拟计算或虚构状态。

### 原型交付与版本管理

用户确认原型后，ChatGPT 应尽可能提供：

1. 可访问或可下载的原型文件。
2. 文件名和版本标识。
3. SHA256 校验值。
4. 原型涵盖的主要交互与状态。
5. 已确认的视觉和功能验收条件。
6. 原型与真实生产业务的边界。

原型必须明确区分演示数据与真实业务数据，不得直接操作生产 IndexedDB。演示记录和模拟计算不能充当真实营养、训练或历史事实。

ChatGPT 临时文件不会自动出现在 Codex 工作区。用户需要将原型文件实际交给 Codex，或提供 Codex 可访问的 GitHub 文件路径。Codex 接收后，应核对文件 SHA256 与交付值；无法获得交付校验值时明确说明核验限制，不得伪称校验一致。

若任务要求长期保存批准基准，Codex 应在仓库相应设计目录保留不可擅自改写的原型及必要说明，记录来源、版本、SHA256、涵盖状态和业务边界。未实际取得文件时，不得宣称已读取或实现该原型；先检查已有工作区、交付目录及仓库设计参考，并报告实际结果。

## 阶段 5：ChatGPT 生成 Codex 指令

每份正式开发指令必须包含以下十二项；不适用项明确写明原因：

1. 项目及任务背景。
2. 需求目标。
3. 当前已知实现及需要核实的事实。
4. 已确认的业务和交互行为。
5. 原型或视觉基准（适用时），包括可访问位置及批准版本。
6. 实施范围及禁止修改的部分。
7. 数据兼容性、安全及历史语义要求。
8. 测试与功能验收标准，包括应执行的命令、场景和预期结果。
9. 视觉验收标准（适用时），包括对照条件和关键状态。
10. 应更新的文档及更新范围，说明哪些持久规则或最新状态需要维护。
11. Git 提交、CI、发布及生产验证要求，明确授权范围及证据。
12. Codex 最终交付回执格式，使用阶段 7 的统一结构。

指令必须具有可执行性和可验证性，不能只有「优化体验」「确保正常」。缺失事实应列为核实步骤；未确认的产品选择不能伪装成已确定实现要求。

视觉任务还必须：

- 明确引用已确认原型及其文件位置、版本和交付校验值，写明需要保留的页面结构、交互流程、状态和组件样式。
- 区分视觉示例与必须满足的业务行为；演示文案和数据不自动成为生产业务要求。
- 尽量完整描述已确认决策和验收条件，减少实施期间反复探索产品决策；不允许 Codex 擅自改变已确认的设计方向。
- 生产环境与原型存在技术限制或无障碍冲突时，应说明差异及影响。涉及重大设计变更时，返回 ChatGPT 与用户重新确认，按阶段 3 停止受影响部分。

## 阶段 6：Codex 开发与验证

Codex 负责：

- 以正式实施和验证为主，优先复用已确认原型与现有生产组件，不重复开展已经完成并确认的普通视觉方案探索。
- 不把独立演示原型直接当成生产业务代码。生产数据继续使用现有业务服务、校验和事务，保留可访问性、真实数据状态及历史兼容性要求。
- 实际读取项目规范和最新开发状态；检查工作区、分支和最新远程 main，记录实际起始 SHA，保护其他未提交工作，不凭旧聊天认定基线。
- 核实当前代码，实施已确认需求。仅修改必要文件，避免无关重构。
- 保护现有 IndexedDB 数据、历史快照、Backup/Restore 和 Sync 兼容性；遵循 [数据保护合同](DATA_PRESERVATION.md) 与相关领域合同，不以清空数据库或重算历史换取新版效果。
- 执行与变更范围匹配的测试，并满足适用的现有工程和发布门槛。不能删除测试、跳过已有必需回归、降低断言或清空数据库来使验证通过。
- 涉及视觉的任务必须实际运行页面、截图并对照已确认原型；在相同视口、字体和主题下核对结构、尺寸、颜色、按钮、间距及相关状态。不能只因数据相同或测试绿色就宣布视觉一致；合同要求与可访问性之间的必要差异应明确记录。
- 检查相关的小屏、字体放大、深色模式、横屏、键盘、弹层滚动和 iPhone Safe Area 场景。检查范围及未覆盖项必须说明。
- 按任务授权和仓库 Git 工作方式完成 Commit、CI 和部署验证；提交前重新核对远程状态，只提交本任务文件，不覆盖他人工作、不强制推送。无安全执行条件时列出阻塞和明确待执行步骤。
- 更新任务指定及实际受影响的持久文档，按项目要求记录开发与验证状态。

必须核对实际页面与批准原型。如果测试与原型冲突，先核实测试保护的真实业务、历史语义和可访问性要求；不得通过削弱测试或数据保护合同解决。需要重大设计调整时，说明冲突和影响，交回 ChatGPT 与用户确认。

验证证据必须分开：

|类别|证据及边界|
|---|---|
|自动化验证|实际执行的类型检查、单元测试、构建和浏览器测试；列出命令、环境和结果|
|视觉验收|实际页面截图与批准基准逐项对照；测试通过不能代替人工视觉检查|
|真实设备验证|实体 iPhone Safari、原有主屏幕 PWA、真实键盘和 Safe Area 的独立证据；浏览器模拟及 WebKit 自动化均不能替代|
|部署验证|对应 Commit 的 CI、Pages 部署结果及实际生产检查；不能从本地构建推断已经上线|

没有物理设备证据的适用项目标记 **Pending（待真机验证）**。纯文档维护按任务范围验证文档、路径和 Git diff，不伪造产品运行证据；具体任务明确不要求的产品测试或部署应如实标为未执行或不适用。自动触发的 CI/Pages 仍报告实际结果。产品开发及发布继续遵循现有工程门槛。

## 阶段 7：Codex 交付回执

完成后必须返回以下统一结构，并让回执独立可读：

1. **任务完成状态及摘要**：完成 / 部分完成 / 未完成，说明完成范围。
2. **实际修改文件清单**：文件路径及具体用途。
3. **关键实现及行为变化**：修改前后行为、保留的业务语义及必要差异。
4. **Git 信息**：分支、起止 Commit SHA、PR 或提交链接、推送状态。
5. **执行的测试命令及实际结果**：标注环境、覆盖范围和失败原因。
6. **原型和生产 UI 对照证据（适用时）**：基准版本、截图位置、对照条件、结论及差异；本地截图不能称为生产截图。
7. **数据兼容性和历史数据保护证据**：适用的版本、迁移、旧数据回归和保护检查；无数据变更也说明依据，不冒充运行验证。
8. **更新的文档**：路径及更新内容；不需要更新的文档说明不适用。
9. **CI、Pages 和正式环境验证状态**：对应 SHA、运行链接、实际结论，分开列出。
10. **未完成事项、已知风险和待真机验证项**：阻塞、待补证据及后续动作。

测试与检查结果统一使用：

- **PASS**：实际执行且通过，有可核对的结果。
- **FAIL**：实际执行但失败，保留失败范围及原因。
- **未执行**：适用但尚未执行，说明原因；不能计入通过。
- **不适用**：不属于本轮范围或该场景不适用，说明依据。

Pending 表示仍待验证，不是 PASS。不能把「代码已提交」表述为「已发布」，不能把「CI 成功」表述为「用户已验收」。不得沿用旧轮测试数量或旧截图冒充本轮结果。

## 阶段 8：ChatGPT 独立验收

用户将 Codex 回执粘贴回 ChatGPT。ChatGPT 应：

- 优先对照自己制作且经用户批准的原型及已确认需求逐项检查；使用既有批准基准的任务按其明确版本验收。
- 对照布局、组件层级、文字、状态、交互和实际数据表现，区分视觉示例与正式业务事实。
- 必要时重新读取 GitHub 的 Commit、代码、测试、文档及部署证据，不只依赖回执自述。
- 检查测试覆盖及缺失证据，确认结果对应本次修改与发布身份。
- 分别判断功能正确性、视觉一致性、数据安全性和发布完成状态。
- 输出明确结论：**通过 / 有条件通过 / 需要修复**。有条件通过应列出条件和待验证项，不能将 Pending 隐藏为通过。
- 未通过时，只针对不符合批准原型或验收条件的部分生成定向修复指令；已验收合格的部分不安排重复开发。若修复改变原确认范围或方向，先按阶段 3 获得确认。

Codex 自述「完成」不能自动代表 ChatGPT 验收通过；ChatGPT 的验收结论也不替代用户的最终确认权。

## 协作边界

- **用户**拥有需求、产品方向和最终确认权。
- **ChatGPT**优先负责需求分析、方案比较、原型制作与迭代、设计确认组织、正式指令与独立验收；用户保留最终确认权。
- **Codex**负责实际代码开发、验证、提交及授权范围内的发布。
- **GitHub**是项目代码、规范和已提交状态的共同事实来源。核对具体分支及 SHA；本地未提交修改、旧聊天和尚未完成的部署不能当作已发布事实。
- 普通 Chat 对话不等于 Codex 已自动执行任务，两者通过用户传递指令与回执。没有实际执行记录，不能宣称代码已修改。
- 连续性由实际可读取的仓库文件保证，不依赖某一次聊天的记忆。
