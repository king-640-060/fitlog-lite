## 4. 已确认的交互规范（逐项约束）

### 4A. 共用纵向拖拽行为

1. 仅左侧宽度足够且 >=44px 高的固定把手启动排序；其余区域的触摸仍然允许原生纵向滚动、输入、选择文本、点击删除、进入子表单。视觉把手可小，但可触控区必须 >=44px。
2. 起拖明确后，被拖动的**原条目视觉**跟手实时移动（画面中从起点到任意中间位置的位移与手指相符），其原位由占位元素维持；相邻条目跨越阈值平滑让位。**不能只在 pointermove 中 `insertBefore` 瞬间交换、不能松手后才显示变化、不能整列表重绘。**
3. 必须处理多次跨项、上下回拖、快速拖动、手指短暂停顿、长列表上下边缘自动滚动、用户中途取消/切出/失去焦点、减少动态效果、鼠标和触摸；取消后原始顺序保留，正常释放才将唯一新顺序写入 draft 并按现有服务持久化。
4. 合法排序范围：整日饮食仅当前餐次；动作排序仅当前训练的动作列表；训练组内 set 不是本轮要求的可拖拽层级，组编辑仍按现有逻辑。模板、当前训练和历史记录不可共享同一个可变对象引用。
5. 排序对象具有稳定 ID；保留食物克数/品牌/营养快照/餐次，保留训练 set ID/重量/次数/备注/老字段。移动不应触发数据校验失败后的部分写，也不能拖跨餐次时悄悄修改餐次。
6. 提供可访问的非手势替代方式（键盘可排序、明确的上下移动或操作菜单），拖拽状态有可读提示，不牺牲 VoiceOver、44px 目标、16px 输入及页面缩放。

### 4B. 饮食模板与四餐次

1. 整日模板只在区域顶部呈现**一组**固定等宽餐次切换；各餐次仅有自己的食物、数量与新增动作，空餐次明确可新增。
2. 切餐次时整块内容形成宽度严格相同的相邻页；按住移动立即跟手，未达阈值回弹，超过阈值落位。顶部导航指示同步，但导航不是唯一发生动画的地方。
3. 任何餐次数量为 0/1/多条、含极长食物名、200% 字体、动态添加/删除后都不得改变容器宽度、水平溢出或改变其他餐次保存值；切出/返回恢复草稿、所选餐次和合理的滚动位置。
4. 原模板 `mode: 'combo'`/未设置 mode、`meal` 缺失的历史项目不丢失；提供原有组合/未分类可访问入口，保留原先应用模板时“实际餐次”对日志的语义，不能自动全部算作早餐。仅顶层分组 UI 改造，不做数据迁移。
5. 选择新餐次只影响当前模板编辑的目标位置，不代表真实食物摄入；保存仍调用已验证的业务服务，错误/撤销保留编辑草稿。

### 4C. 训练动作编辑和名称

1. 动作列表卡更紧凑，但头部动作名称与右侧删除/改名、组号、重量kg、次数、组备注、添加一组以及训练完成入口保持可访问。
2. 「＋添加动作」必须保留**现有动作库搜索/选择与可选新建动作**；新增动作后可输入名称；已有动作可通过明确“改名”操作修改本次记录中的动作显示名称，输入为空拒绝保存，取消保持原值。输入时中文 IME 不被重排/焦点丢失，失败时保留文本。
3. `WorkoutExercise.exerciseName` 与 `Workout.name` 严格区分；本次快照改名不得自动修改 `Exercise.name`、原动作库列表、模板定义或已完成历史。`exerciseId` 标识关联、分析的 ID-first 语义和训练统计依旧有效；不能用名称更改实现隐含的库记录删除/重建。若 current model 的全局身份与局部快照有真正不兼容风险，先给出可验证差异，别偷偷改分析匹配规则。
4. 命名、拖动、增删组、Autosave、返回/后台、训练完成的并发必须受现有 source fingerprint/写队列约束。没有改组时仅改名称不应把历史 notes/set 未知字段强制归一化。未命名/合法遗留名称按照当前既有规则显示，原有整次训练命名功能继续正常。
5. 训练模板内动作列表如存在同类上/下箭头，应进入同类审计；可按同一把手/紧凑布局改造，但 **WorkoutTemplateExercise** 和 **WorkoutExercise** 的保存路径、快照与模板应用必须各自保持原有事务语义。

### 4D. 进度三级导航与零跳动合同

1. **层级 1**：趋势 ↔ 日历 ↔ 报告。此层切换整页容器；报告二三级导航已作为完整报告页面结构预先存在，跟整页一起平移，而不是换页后增加高度。
2. **层级 2**：日常综合报告 ↔ 营养周期报告。层级 1 的标签、位置、横向滚动偏移必须保持不变；本级与对应报告内容一起水平滑动，三级是否展示仅根据真正可用的报告类型，且布局预先预留/协调，不后插顶页。
3. **层级 3**：日报 ↔ 周报 ↔ 月报 ↔ 自定义。层级 1、层级 2 的导航**必须完全静止**：滑动指示器、标签、容器屏幕几何均不发生位移；只有第三级选中状态及当前报表内容随手指移动。不得将第二、三级作为同一个横滑轨道子节点而共同移动。
4. 每层同时支持：点击任意目标标签、在对应导航区域水平拖动、在该层所属内容区域滑动相邻页。要有明确的嵌套手势方向仲裁：点击、纵向页面滚动、横向图表、日期轨、iOS 边缘返回、顶层五 Tab 手势、输入/Sheet 的优先级按既有规范；不得一个滑动同时切两层。触摸取消/指针捕获变化必须正常恢复。
5. 滑动中内容跟手位移，不是直接瞬间换页或只动画导航胶囊；松手后距/速阈值明确、一页相邻切换或回弹；同一动画只有一个 scroll/transform 真值，避免 CSS 动画和 JS scroll 双重竞争。不要在 settle callback 重置轨道造成 32px 回跳。
6. 任意一级进出前、中、后，当前页面**宽度一致**、无横向溢出；报告页二、三级一开始就有布局，不允许过渡结束突然向下顶约124px。日历七列及合法滚动高度不受右侧更长报告撑高。
7. 各主页面及报告子页面的纵向滚动位置独立；在报告中部切日历/趋势再返回可恢复报告原位置，不因邻页高度被浏览器 clamp 或滚动条借用出现闪跳。空状态、加载/错误态和动态数据刷新遵守同一零跳动原则。
8. 两种报告类型在切换后应显示对应真实内容；不能出现“周报”标签却展示旧日报。日期范围、营养周期筛选与报告已有限制保留；**不要通过伪数据、预生成一整份用户私密历史或强制重跑所有报表来假装有切页预览**。惰性/受限只读预加载，失败展示稳定状态，正确取消过期任务/订阅。

### 4E. 指定食物底部按钮

1. 选食物页的「计算建议份量／改为记录实际摄入」与预览页的「返回选择食物／确认已实际吃下」在同一**共享 Sheet footer** 体系内，主次强调、逻辑顺序、宽度/间距和左右边距一致，布局在适用 Safe Area 下正确。
2. 内容高度短/长、选中 1–4 食物、搜索过滤、预览详情长、键盘弹出/收起、系统工具栏收缩、320px、200% 字体，按钮均不能遮住最后一项，不能固定在随意的像素高度，不能离实际 Sheet 底部异常远、压在关闭区域或滚动内容之上。
3. 采用现有 Sheet/VisualViewport 协调器；可视空间不足时，按 `docs/AUTO_PORTION_GOAL_DESELECT_V021.md` 已批准规则使 footer 加入同一原生滚动流，不能另外加私有全局键盘监听器/全屏滚动锁。
4. 选择/推荐/预览/返回都是草稿零写入；只有明确确认实际食用、选择真实餐次并经过原来的数据守卫才能写入 FoodLog。所有营养与目标差额使用真实保存服务，不得引用 v0.9 的模拟数值。查询/选中/原滚动位置返回时保存，防止双点重复写入。

## 7. 数据兼容性、安全和历史语义

- 生产库名始终 `fitlog-lite-db`；当前文档基线 Dexie13/IndexedDB130/22 stores、Backup14、Restore1–14、Sync/envelope1；实施须以当时实际 main 核实并维持受支持范围。预计**无需 schema/index/Backup 格式变更**。任何必要 schema 变化必须有显式安全迁移并事先报告与测试。
- 永不通过 IndexedDB 清库、数据库改名、重设 localStorage、删除个人数据或重新计算历史快照解决布局/手势问题；不改变食品 kcal 原值、FoodLog/Workout 事实及旧模板 fallback。
