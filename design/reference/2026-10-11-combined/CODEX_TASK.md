## A. 饮食页：「特殊饮食」改为餐次列表后的低强调入口

1. 核实 `src/main.ts` 内 `renderFoodPage` 的原有顺序：剩余目标 → `dietEventsHtml` → 当日饮食标题与 `food-meals`。将**饮食主页面**的特殊饮食入口移至全部实际餐次卡片之后；保留其他页面（如 Calendar Day Detail）的特殊饮食独立展示功能。
2. 删除原处醒目的标题加右侧「标记放纵餐」展示，替换为餐次列表底部一条安静、≥44px 可点的辅助入口，视觉详见原型。没有记录显示「特殊饮食 / 添加标记」，有记录显示正确的「已标记 N 条」；**N 来自所选本地日期的 DietEvent 实际数量**。多条记录不能被错误折叠为 1。
3. 点击入口复用现有 `showDietEvent`、`bindDietEvents`、现有 sheet 及增删改保存；有记录时可查看**完整**记录列表、选择编辑、继续新增（受现有整天/单餐约束）。原型里的示范记录不是真数据。
4. 保留日期切换、已有 DietEvent 的整天/单餐范围、备注、可选手工/照片估算、删除确认以及 Calendar / Reports / Backup / Restore / Sync 对原有数据的读取。粗略热量**不计入** FoodLog 摄入、目标、剩余与报告实际统计，不改变历史快照。
5. Food 的 `food-meals`、可能存在的未分类记录与 nav Safe Area 均保留。移动到列表末尾后最后一条入口须可完整滚到固定底部导航上方。不要修改正常餐次卡片层级。

## B. 训练模板：「添加模板动作」无结果状态

## C. 进度/日历：十类图标、详情折叠操作、精确删除

### C1. 日历本身增加第十类「计划」

1. 原有九类 `food / strength / cardio / pelvic / weight / dietEvent / habit / sleep / water` **顺序稳定**，新增 `plan` 作为第十类。规划日期有实际 Task 且 `Task.date` 为所选业务日时点亮「计划」图标，不要求已经完成；计划状态是**计划存在**，不能混称训练或饮食完成。
2. 日期单元采用 **3 列 × 4 行图标矩阵**：九类按原顺序，第四行中间置「计划」；没有事实的类别保持空槽，仍保持稳定语义位置，不显示虚构记录、不加 `+N`。同步更新图例、日期可访问性文字、日期详情以及读取汇总。当前七列日历的触摸目标 ≥44px，320px 不横溢。
3. 日期行允许为了第十个图标做必要的局部增高/间距优化，不得让标记相互重叠或缩到无法辨认。依据 `prototypes/` 的批准版及 `references/calendar_original.jpg` 的现状。今天、选中日和跨月格的表现不退化。

### C2. 日期详情布局与操作

1. 当前 `showCalendarDaySheet` 的九类可展开真实记录升级为**十类**；依原型提供适于手机的两列、五行紧凑分类概览，同时保留展开/查看每一类**全部**真实明细的能力，不能因为使用紧凑概览丢掉原生 disclosure、历史快照或信息完整性。计划条目显示任务信息与完成状态，兼顾未排日期/其他日期隔离。
2. 下方默认折叠为两个入口：「快捷记录」与「管理 / 删除当天记录」。按需展开；避免在页面底部永久堆放十个大按钮。
3. 「快捷记录」展开提供十类入口；每个入口应复用真实已有业务流程，正确携带所选业务日期、返回目标与键盘/Sheet 生命周期。若某个类别在现有工程中没有安全的直接新增入口，可以先跳转到该类别既有的记录页/管理流并带上日期，**不可用模拟写入代替**。睡眠使用现有夜间归属规则；计划进入已有 Task 创建并预置日期；特殊饮食复用 DietEvent。
4. 「管理 / 删除当天记录」展开可选择十类中的任意单类、多类或全部有记录类别。先从同一份真实事实源生成**每类实际数量及删除预览**，再明确二次确认；确认文案必须列出日期、具体类别与数量。删除成功后原 Sheet、日历图标、日报/周报/月报、统计等关联视图刷新一致；失败原子回滚，不得出现部分成功而 UI 声称全清空。
5. 删除范围只限于**指定日期归属的实际记录**：饮食 FoodLogs；力量 Workouts；有氧 CardioSessions；凯格尔 PelvicFloorSessions；体重 Weight；特殊饮食 DietEvents；习惯仅 HabitCheckIns、不删 Habit 定义；睡眠仅按既有 business-date resolver 归属的已记录对象（核对跨夜边界与多段记录）；饮水 WaterLogs；计划仅 `Task.date` 对应日期的 Task，不删 Tag 定义或其他日期安排。使用明确、可审计的精确 ID/日期条件和数据库事务。
6. **营养目标是独立于「十类图标」的业务数据**：不能静默地随「仅删除饮食记录」被清除。若用户要清空该日保存的 NutritionTarget，确认预览中必须单独列「同时删除当天已保存营养目标」的可选择项和现有目标信息，且默认不勾选；不得清空周期定义、营养模板或日程配置。保留原七类 `clearDayRecords` 的兼容函数与调用边界，新增面向十类选择的**单独受控 API**，不要悄悄扩大旧 API 的破坏范围。
7. 删除前可以提供已有备份能力的入口，但不得未经用户明确确认自动发起 Restore、站点数据清空或跨日全量删除。不能清空食物库、动作库、饮食/训练模板、习惯定义、任务标签或不同日期事实。最后一次确认明确「不可撤销」。
8. 保留已有 Daily Records Summary 的日期、本地时区与历史未知语义；不把没有记录转为 0 个完成任务、不把计划当完成、不把 DietEvent 粗估算计入 kcal。

### C3. 报告/日历的两项局部视觉修复

1. 日报日期 `10月11日`（以真实选择日期为准）在左右箭头中间居中，字号建议 16–17px，不要被日期选择 button 的默认样式放大。左/右 44px 点击区域对称，原有日期选择、切换、今日返回保持正常，周/月报标题不受影响。参考 `references/report_original.png`。
2. 修复报告、日历及日期详情中力量、有氧、凯格尔、体重等分类图标在深色模式仍使用亮色浅底的问题：**优先使用现有深浅主题 Token 或其主题派生色**，只修改受影响类别组件，不全局反转图标或破坏语义颜色。对照 `references/report_categories_original.png`、`references/calendar_original.jpg`、`references/day_sheet_original.png`。浅色模式仍清晰，暗色无突兀白底，颜色对比度可读。

## D. 高度自定义营养周期 + 饮食模板排程

### D1. 用户确认的交互行为

1. 支持自定义名称、开始和结束本地日期；任意连续周期长度在明确合理上限内；包含所选首尾日期，日期用本地 `YYYY-MM-DD`，不能用 `toISOString().slice(0,10)`。
2. 关联**现有营养模板（NutritionStrategy）**，读取模板中真实的 2 个或更多日方案（例「训练日」「休息日」），可**任意分配到具体日期**，不强制同一星期几的固定重复规则；每一周可展开、收起。
3. 支持单日点选、多日、跨周多选、本周全选、工作日/周末选择，并对选定日期批量应用某个**营养日方案**；允许单日覆盖。不指定应表示没有新的排程目标，不代表删除已有已保存营养目标。
4. 每个日期还可以**独立**选择现有饮食模板或无模板，不强制绑定某种日方案；允许只改营养目标、不改饮食模板（反之亦然），不能因未选一个字段而清空另一个字段。
5. 复制本周到其他周并按实际目标周的日期处理缺少天数/周期首尾边界；覆盖已安排内容前提供对比与明确确认。
6. 保存前提供日期→日方案→营养值→饮食模板的范围预览，指出未分配日期与冲突日期。保留当前营养模板的多变体与阶段切换、策略来源、历史目标快照；不因修改/归档模板重算已有目标。
7. 排程不是实际摄入记录：**安排饮食模板绝不自动新建 FoodLog，也不能计为已吃过的食物或营养达标。** 真实摄入需用户当日显式确认，复用现有 DietTemplate 服务、快照与冲突处理。
8. 按日营养目标若需落地为已保存的 `NutritionTarget`，须通过明确的预览→应用确认，复用或扩展现有目标服务的校验与事务；对已有同日期目标要明示保留/覆盖，不静默覆盖。可以先持久保存可预览的周期排程，再按用户确认的动作显式应用目标，但必须在交付回执清楚说明排程与已保存目标的区分，并提供真实可用的应用路径，不能只保存看得见却不起作用的演示 UI。
9. 对周期、日期排程、单日替换/取消进行可追溯和合理冲突处理。已记录食物、历史训练、已保存目标、已启用 NutritionStrategyPhase、策略历史不得被复写；不要自动回填或清空过去的事实。

### D2. 数据安全与持久化

- 这是一个**持久化业务安排**，不得只写内存或设备配置 LocalStorage 冒充可备份、可同步的业务事实。检查当前 `NutritionStrategyTemplate/Variant/Phase`、`NutritionTarget`、`DietTemplate`、`Task` 等模型，优先重用现有语义；若需新业务实体/索引，新增明确的 Dexie 正向迁移和索引、完整旧版本 Restore 兼容、备份与加密 GitHub Sync 适配以及迁移/恢复/事务回滚测试。不能偷偷改变现有 20 个 store 或原数据库身份。
- 同一日期的周期排程发生冲突时明确提示与选择，不以最后一次不提示写入覆盖用户已经保存的目标或其他周期。周期结束/编辑/归档只影响排程定义和将来选择，不重算实际历史事实。
- 不能把原型中的示例模板、模拟值、演示热量/训练指标填进生产数据库；生产展示来自真实模板或「未指定」。
- 逐项测试数据存在/缺失/目标冲突/模板被删除或归档/大量天数/跨年/当地日期与 DST/刷新后持久保留/备份恢复/多标签打开等场景。
