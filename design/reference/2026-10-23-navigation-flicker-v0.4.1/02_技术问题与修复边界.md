# v0.4 闪烁问题：可复核技术链路

## 来源等级

**用户观察（确定）：** 两段生产录屏显示五个 Tab 导航均存在明显“闪一下／刷新”的感知，训练页有明显的二次落位。此观察优先于先前自动化中间帧 PASS。

**实际仓库代码（确定）：** 当前 main `src/main.ts`：

```ts
// src/main.ts near 339
if (!pageNavigation) pageNavigation = createPageNavigation({
  tabs: mainTabs, stage: app.querySelector('.page-swipe-stage')!,
  current: app.querySelector('.page-current')!, nav: app.querySelector('.bottom-nav')!,
  active: () => activeTab, prepare: prepareTabPreview,
  commit: async tab => { activeTab = tab; await render() }, fail,
})

// src/main.ts near 326–353, shortened
if (previousNav) {
  const fresh = document.createElement('div'); fresh.innerHTML = markup
  app.querySelector('.topbar')!.replaceWith(fresh.querySelector('.topbar')!)
  if (!previousView) app.querySelector('#view')!.replaceWith(fresh.querySelector('#view')!)
}
// ... rerender target body after DOM replacement
switch (targetTab) { /* renderTodayPage, renderPlanPage, renderFoodPage,
                         renderWorkoutPage, renderProgressPage */ }
```

`src/ui/horizontalNavigation.ts` 在 `finish()` 中先 `await options.commit(target)` 再 `clean()` 删除当前 `.page-preview`。如果 `render()` 与预览渲染结果、数据时序、绑定或布局不完全一致，就会在同一次导航的视觉交接处产生二次刷新。

**解释机制（强假设，尚需精确复现证实）：** 预览 renderer 和正式 renderer 不是同一个 DOM。`prepareTabPreview()` 创建 inert/aria-hidden，只读渲染器在 `if (preview) return` 时跳过正式监听/订阅，还移除了内部 id/aria-live。于是 commit 函数二次查询并重建。训练页 `renderWorkoutPage` 在真实 `findOpenWorkout` 与多项 Dexie 查询后才写入 `view.innerHTML`，二次布局差异更明显。

## 绝不能采用的虚假修复

- 仅 `.page-preview` 加 opacity/backdrop、fade、mask、skeleton、delay，或缩短动画，使肉眼“较难看见”仍不满足。
- 预览 node 扒掉 inert 并在未绑定事件的情况下直接替换 active DOM；会把功能性 Bug 藏在视觉通过后面。
- 预览和正式页各订阅一次 liveQuery，造成后台多次响应／内存增长。
- `replaceWith()` 等仍发生在用户可见交接帧，依赖设备速度幸运地看不见。
- 保存时强行重置 `scrollTop=0`、训练 editor 回到默认态、Food day 跳回今天。
- 借 Bugfix 擅自修改 v0.7 的美术设计、进度二级导航或营养四色进度条。

## 推荐机制与性能约束

1. 仔细设计 `read-only preview → active page` 的**一次性可见移交**：
   - 若维持 preview：需在不改变已显示像素的前提下原地激活正确业务绑定，并恢复 `id`、`aria`、可聚焦控件状态；提供保序交接的状态/资源所有权证明。
   - 若预先构建真正的目标视图：准备阶段不得写库，正式激活时注册监听/订阅一次，目标 UI 只创建／显示一次；离屏视图保证 inert/hidden，避免背景 CPU 和键盘焦点。
   - 若仍使用双 DOM：必须严格实测视觉绝无差异，交接与 scroll 合成在同一帧，且消除 Commit 后的第二次业务呈现。
2. 导航取消要原子：Abort pending reads, end rAF, detach previews, restore current interaction。只保留确有必要的已访问页面 DOM，并清理非活跃 observer、timer、订阅；不能让无界缓存逐次增长。
3. 对已存在数据状态，营养数字、图表、训练统计必须从第一次可见帧就最终正确；不允许从 0 数起、进场淡入、训练卡片空→满突变。
4. 对未加载的目标保持当前稳定页面直到 ready；禁空白触发导航成功。异常时保持 current activeTab 和 aria-current，给予既有错误反馈，不留锁定态。
5. 连续点击/拖动的最后用户意图优先；拒绝迟到 Promise/render 夺回焦点/目标。
