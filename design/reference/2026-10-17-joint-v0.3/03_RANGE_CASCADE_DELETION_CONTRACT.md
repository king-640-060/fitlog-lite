# 新批准删除语义：模板归属六类 + 使用日期区间的全部每日健康事实（唯独计划不删）

**严重危险操作。** 这是用户在上一轮发布六类删除后，新明确批准的扩大范围。开发功能 ≠ 立即授权删除真实设备个人数据。

## 1. “模板时间范围”的权威来源

- 当前模板 `nutritionStrategyPhases` 的每个 `[startDate, endDate]`，包括历史/结束阶段；缺少 endDate 的进行中阶段只截到**预览与确认事务一致的本地今天**，不能无界延伸到遥远未来。
- 属于模板的每个 `nutritionCycles` 的 `[startDate,endDate]`，包括已归档、历史和**明确排定的未来日期**。不能只看 `nutritionCycleDays` 已分配日期：周期本身定义了连续分析区间（其每一天即使未分配方案也属于周期）。
- 将这些闭区间转成**日期集合并集**，合并连续段但不把两个不连续段之间的间隔日误删。阶段与周期重合的日期只计/删一次。不得只按模板名称或营养数值生成日期。
- 当前模板可能从未启用也没有周期：不构造时间范围，仅按归属 ID 删除原六类；**不删除任何独立健康事实**。
- 只读预览显示每个来源和合并后的生效段、日数、所选模板名称、当前/历史/未来状态；“未来”表示这些明确周期日期将被清空其既有未来记录及排程，不能宣称还未发生的事实已记录。运行时使用本地业务日期，而非 UTC 午夜边界。

## 2. 删除对象：按“归属ID集合”和“日期集合”精确匹配

### A. 原六类归属对象，始终删除

1. `nutritionStrategyTemplates`：目标模板本身；
2. `nutritionStrategyVariants`：owned templateId 的日方案；
3. `nutritionStrategyPhases`：owned templateId 的所有阶段；
4. `nutritionTargets`：来源字段 `strategySelection`/`cycleSelection` 引用目标模板及 owned variant/phase/cycle 的目标，**即使不落在该模板日期并集内**也要删除，防悬空引用；
5. `nutritionCycles`：该模板全部周期；
6. `nutritionCycleDays`：被删周期全部日期行，及确认属该模板但违反归属的一致性问题按冲突无损拒绝，不破坏他人周期。

### B. 新增日期范围“健康事实”，按所有命中日期删除

- `foodLogs`（真实吃下的各餐、份量/宏量快照）；
- `weights`（日期上的全部重量记录，包括同日多个记录）；
- `waterLogs`（所有日期范围内的饮水事件，不取当天总和误删其他日期）；
- `sleepSessions`（**按所属夜晚 `resolveSleepBusinessDate`**，不是简单 `recordDate/startTime` 或起床当天，跨午夜整段会话算一个业务夜晚，按匹配的整条 session ID 删除；对 in-progress active session 也需显式审计其夜晚、处理 UI 活跃状态并在预览里说明，不能静默留存或打断计时）；
- `workouts`（整条力量训练实体，按保存业务 `date`，其内部 set 均随整条记录删除）；
- `cardioSessions`（整条有氧训练）；
- `pelvicFloorSessions`（专项/盆底训练）；
- `dietEvents`（真实日期上保存的特殊饮食事件/备注）；
- `habitCheckIns`（日期上的习惯打卡事实）。

**第六类 `nutritionTargets` 还必须额外删除“日期并集内所有目标”**，包括手动创建、饮食模板应用或其他来源的日目标；选中的最终 target IDs = 六类模板归属目标 ∪ 日期并集命中目标，按 ID 去重。预览需**拆分统计来源相关目标和额外区间目标**，避免用户不知道手动目标也会损失。

### C. 全部保留、写保护

- **计划业务：** `tasks`（其中的 `subtasks`、任务完成状态、所有日期）、`taskTags`；不得调用 `dayDeletionSources.plan`。**本轮不删用户的计划/待办**。
- **跨日期可复用的定义：** `foods`、`exercises`、`workoutTemplates`、`dietTemplates`、`habits` 的定义（只删除对应打卡事实）；不能因有一条引用在区间内就删除全库模板。可以留下未被引用的定义，不能做自动 garbage collection。
- **区间外的所有健康事实（上面 B 的九类）**；以及与模板无关、日期不在并集内的 nutritionTargets、其他营养模板/日方案/阶段/周期/排程。
- DB、Backup、Sync、设备设置、AI/Voice/Appearance/Reference、旧真实资料等所有其他数据。如果将来加了健康事实存储表，要先核对并更新明确批准的清单；禁止对未知表“全部清空”。

## 3. 冲突与异常

- 用户确认日常**不存在跨模板日期范围重叠**；因此正常删除不得制造复杂交互。然而正式服务必须检测脏数据、旧档、已归档周期、交叉归属、缺失日方案/phase、重复合并等造成的日期冲突。
- 如果影响日期也被**别的营养模板**的阶段或周期覆盖、或保留的 NutritionTarget 存在冲突来源，预览用日期、模板 ID、对象数说明，按钮禁用且拒绝整个事务，**不要默默删除别人报告共用的事实**；须回报用户选择修复方案，不提供未经批准的越界覆盖强制选项。
- 同一模板 phase 与自己 cycle 交叠完全正常：取并集，不阻断。
- 对没有阶段也没有周期的模板，仍允许六类删除，但不能以“模板曾经启用过”猜测历史健康事实范围。
- 若有 active/in-progress 睡眠/训练落入删除范围，必须准确列出与处理运行态/后台计时/重绘。无法安全协调时，整个删除拒绝并提示解决路径，不能先删部分后让 UI 幽灵继续运行。
- 不得根据时间范围去删 `food` 库、`exercise` 动作定义、独立 diet template、habit 定义和计划记录；时间范围关联是**语义选择条件**，不是数据库所有权。对于健康事实全部删除这是用户已知情同意的特殊规则，必须在 UI 明示。

## 4. 两段式确认 + 单一事务

1. **只读事务预览**：精确读全部涉及的表及能检测跨模板冲突的六表/事实表；计算日期并集、六类 owned ID、九类 date ID 和额外 targets IDs；显示各项数目、首末日期/多段、总数、已发生/未来区分、保留项目，注明**“这些记录按日期删除，可能并非直接由模板产生”**。指纹须包含范围来源和所有潜在对象的可比快照，不只是已选对象。
2. 用户风险确认勾选后，再经过第二次清晰的永久删除确认。取消、Sheet 关闭、从其他页导航离开不写入。
3. **一个 Dexie `rw` 事务**写锁覆盖涉及的**全部读写表**（原六表+九个健康事实表，和冲突检查中必须保持一致性的任意读表/计划只读校验表）；在事务内重读并重新计算完整指纹+时间并集+候选IDs+冲突及本地当天边界。有一项变化就拒绝，要求重新预览。禁止在活动事务中等待 `window.confirm`、网络、UI 或 timeout。
4. 严格按**精确 ID**删除，不“清空表”，不以 min(date)/max(date) 的大跨度区间粗删，不复用会动 plan 的旧清日方法。
5. 事务内验证所有将保留的行 = 删除前快照减去批准 ID 集合，六类再做来源、周期排程、营养目标引用一致性检验，单条失败整体 rollback。对计划定义/共用定义及所有区间外事实做只读快照并作为不变量核实；给出前后逐表 hash 证据。跨 tab 异常写入以 IndexedDB 事务序列化与重验防 stale。
6. 成功后刷新 Today/Calendar/Progress/Report/模板列表/活动睡眠与训练状态；原周期报告选择器不再提供已删周期，普通报告按剩余事实展示，不回填伪历史，区间外数据继续存在。

**删除是当前 IDB 数据不可撤回。** 不可承诺所有旧离线备份/第三方副本、未同步的远端加密数据都自动销毁；导入旧 Backup14 可能恢复历史，Sync1 仍遵从原现有合同。不得为了“彻底”而删除用户备份/清远端仓库/自动触发额外同步，未经明确授权不能做。

## 5. 数据结构版本硬约束

当前 Dexie schema version **13 / 22 stores**；Backup14、Restore1–14、Sync1/envelope1。**优先零 schema 变更**。如现有 store 在不升版本的情况下不可保证上述合同，先停止并给可审计的迁移提案，不能自行改为“删全部数据”或改备份版本。

禁止接触用户真实 iPhone PWA 的现有模板/健康事实。所有危险操作只用合成 IndexedDB 独立 DB name、隔离 profile；用户授权的是功能实现，不是一次真实数据清除。
